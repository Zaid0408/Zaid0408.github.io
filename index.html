01 halcyon-past/quarantine #64 · merged · Python https://github.com/halcyon-past/quarantine/pull/64

A GCS store for failed jobs

quarantine is a Python library for a loop over many items. You mark the function with @quarantine. If one item throws, the library saves that item and the full error, and the rest of the loop keeps running. Afterwards quarantine retry runs only the saved failures. By default those failures sit in a local .quarantine/ folder, so each machine has its own copy. I added a Google Cloud Storage backend so every worker writes into one bucket, using a path like gs://bucket/prefix.

Constraint

Two workers must never take the same record number. S3 can refuse a write that would overwrite, with If-None-Match: *. GCS has no equivalent header. Deleting an object on GCS raises NotFound where S3 does not, so routine cleanup races. A reader must not observe a half-written record.

Decision

A zero-byte .claim object with if_generation_match=0, which means write only if no live generation exists. The loser gets 412 and takes the next number. meta.json is uploaded last, and readers ignore a prefix that does not have it. Cleanup treats NotFound as a benign race. CI runs against fake-gcs-server, with a 90% coverage gate on macOS, Windows, and Linux.

What fails otherwise

Both workers stamp the same id, or a retried delete fails the job, or a reader picks up a record that is only half there.

02 GDGBabcockUniversity #55 · merged · FastAPI https://github.com/GDGBabcockUniversity/gdg-babcock-hacktoberfest-2026/pull/55

A sliding-window log at 100 requests per second

Login, register, and the LLM grading endpoints of an exam platform needed a limit that still holds when two windows meet. A fixed counter allows a double burst at that boundary. This one is a sliding-window log.

Constraint

Count, check, and increment have to be one atomic step, or two requests both read 99 and both pass. Pod clocks drift, so the timestamp cannot come from the application. Login and register have no user yet. The grading routes do, and one route must not spend another route’s budget.

Decision

A Redis sorted set, one member per request, score equal to Redis TIME. The whole sequence runs in one Lua script. Login and register are keyed by client IP. Grade and override are keyed by user id plus the endpoint. That user id is read from the JWT by a FastAPI dependency the app already had. Eight integration tests, run locally, in the backend container, and in CI with redis:7-alpine.

What fails otherwise

The limit of 100 becomes 101 under concurrency, or 200 in a few milliseconds at the window boundary. A key with no TTL never resets. That second bug is the earlier fix in scamshield-api #80.

01 Inventory reservation · personal project https://github.com/Zaid0408/Inventory-reservation-Analytics

Stock that cannot be sold twice

  • What it is Two services, order and inventory. Several orders can hit one product at the same time, and an order that nobody confirms has to give the stock back.
  • How it solves it POST /orders, POST /orders/{orderId}/confirm, and POST /orders/{orderId}/cancel. Direct exchanges, with a queue per event: order.created.queue, order.confirmed.queue, order.cancelled.queue, reservation.ttl.queue (no consumer), reservation.expired.queue, and dead.letter.queue. The inventory consumer locks the product row with SELECT … FOR UPDATE.
  • Execution flow POST /orders saves the order and publishes to order.exchange with routing key order.created. That message lands on order.created.queue. Inventory locks the row, moves stock from available to reserved, and publishes onto reservation.ttl.queue. When the TTL expires, RabbitMQ dead-letters the message onto reservation.expired.queue, and that consumer releases the stock. Confirm and cancel take the same path through order.confirmed and order.cancelled.
  • Tech stack Java, Spring Boot, RabbitMQ, Spring Data JPA, PostgreSQL, Docker Compose.
  • Misc A reservation only moves RESERVED → CONFIRMED, CANCELLED, or EXPIRED. Available and reserved are separate counters. A unique constraint on order_id stops a redelivered message from reserving twice. After 3 listener retries with exponential backoff, the message goes to the dead-letter queue. Six durable queues across three exchanges.

02 Order tracking · Java · Spring Boot · RabbitMQ https://github.com/Zaid0408/OrderTrackingAnalytics

One event, three consumers, none of them coupled

  • What it is One Spring Boot app. Placing an order should send an email, send an SMS, and update a live count. If email fails, SMS and the dashboard still run.
  • How it solves it POST /api/orders accepts the order. GET /api/metrics returns the counts. One fanout exchange, fanout.exchange, bound to queue.fanout.email, queue.fanout.sms, and queue.fanout.analytics. No routing keys. The dashboard subscribes to STOMP /topic/metrics on /ws.
  • Execution flow POST /api/orders returns 201 and publishes to fanout.exchange. RabbitMQ copies that message onto the three queues. EmailNotificationConsumer writes an EMAIL log and increments the email count. SmsNotificationConsumer does the same for SMS. AnalyticsConsumer increments the event count and pushes the metrics to /topic/metrics.
  • Tech stack Java, Spring Boot, RabbitMQ, WebSocket (STOMP), Spring Data JPA, H2, Lombok.
  • Misc The counters are AtomicLong, because the three consumers increment at the same time. Notification logs are EMAIL or SMS, with status SENT or FAILED. These queues have no dead-letter setup. Inventory is the project where retries and a dead-letter queue are wired. H2 is the database in this repo, so it runs without a separate database.

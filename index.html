01 ms-feedback · owned end to end · Suki AI

Feedback that can be submitted once

The single platform service that stores clinician feedback on AI-generated notes, summaries, QnA responses, and medical forms. Two gRPC endpoints over MySQL.

Constraint

Analytics has to trust the dataset. A second submission for the same item would rewrite history. Organization and user cannot come from the request body, or a caller can attribute feedback to someone else.

Decision

Multi-tenant identity is taken from platform metadata. A submit-once rule makes the row immutable, and a repeat returns AlreadyExists. Shipped with unit tests and service-level gRPC integration tests.

What fails otherwise

Every product surface invents its own feedback table, or the service believes whatever organization id the client sends.

In production at Suki. The repository is internal.

02 Inventory reservation · personal project

Stock that cannot be sold twice

Two services. Several orders can hit one product at the same moment, and an order that is never confirmed has to give the stock back.

Constraint

A popular product is contended enough that optimistic version checks would thrash, and the critical section is short enough that holding the row is cheap. RabbitMQ is at-least-once, so a redelivery must not reserve twice. Expiry has to happen without Redis or cron.

Decision

Pessimistic lock on the product row. Separate available and reserved counters. Confirm-after-expire and double-cancel fail instead of moving the numbers. When the TTL fires, the message dead-letters into a queue that releases the stock. A unique constraint on order_id makes the redelivery a no-op. Six durable queues across three exchanges; anything still failing after three retries with exponential backoff goes to a dead-letter exchange.

What fails otherwise

Two orders both read the same available count and both commit. A redelivered message reserves the unit again. An expired reservation can still be confirmed, and the counters drift.

03 halcyon-past/quarantine #64 · merged

A claim only one worker can win

quarantine (opens in a new tab) sets a bad record aside so a loop of 10,000 can finish. I added a Google Cloud Storage backend so a fleet of workers can share one quarantine instead of each writing to its own disk.

Constraint

Two workers must never take the same record number. Deleting an object on GCS raises NotFound where S3 does not, so routine cleanup races. A reader must not observe a half-written record.

Decision

A zero-byte .claim object with if_generation_match=0. The loser of the race takes the next number. Cleanup treats NotFound as a benign race. A commit protocol hides the record until the write is finished. CI runs against fake-gcs-server, with a 90% coverage gate on macOS, Windows, and Linux.

What fails otherwise

Both workers stamp the same id, or a retried delete fails the job, or a reader picks up a record that is only half there.

Same race as the inventory oversell, opposite tool. The product row is hot and the lock is short, so that service waits on the row. A claim id is almost never contended, so a generation precondition is the whole mechanism.

04 GDGBabcockUniversity #55 · merged · FastAPI

A limit that holds at the boundary

A distributed sliding window at 100 requests per second, in front of authentication and the LLM grading endpoints of an exam platform.

Constraint

The check and the increment have to be one atomic step. Application clocks disagree across pods. Auth and grading are different keys: client IP, and authenticated user id.

Decision

A Redis sorted set, one entry per request, score equal to the server timestamp. The count, the check, and the increment run inside a Lua script on the server. Idle keys expire themselves. Eight integration tests, run locally, in the backend container, and in CI with a redis:7-alpine service.

What fails otherwise

Two concurrent requests both observe 99 and both pass, and the limit of 100 becomes 101. A key with no TTL never resets its window. That second bug is the follow-up in scamshield-api #80 (opens in a new tab).
